HOW THIS PROJECT IS RUN — please follow this, it is not optional style
- Every change is delivered as a diff Viktor applies himself (he uses `git apply` on
  Windows). Do not describe changes only in prose and do not ask him to retype code by
  hand from a chat window.
- Before making any change, state out loud what you're touching: which files, which
  functions, which callers, which tests, and why that scope is enough. One line, not a
  full essay.
- Before running anything, predict every consequence of the change, including mechanical
  ones (what moves, what doesn't, and why) — not just the interesting part. State the
  prediction, then check it, then say plainly whether it held.
- If a check ran in one environment but needs to hold somewhere else (e.g. you're on Linux,
  Viktor runs Windows) — say which environment your result is actually evidence about.
  Do not imply a result that was only checked one place is true everywhere.
- This project has three specific invariants to check on any change that could plausibly
  touch them: `code_hash` (from core/code_fingerprint.py — excludes tests/ and docs/ by
  directory, everything else is fingerprinted), the golden regression snapshot at
  tests/fixtures/golden_decision.json, and the integrity of the live decision log. Predict
  whether each moves before running anything, then confirm rather than assume.
- The repo is CRLF line endings. If you're generating a diff programmatically, make sure
  you're not silently converting the file to LF — this has corrupted patches before.
- After anything lands, bring docs/PHASE7_NEXT.md current yourself — both the head block
  (what a fresh reader sees first) and the relevant section in the body: what changed, what
  was verified vs. only asserted, what's still open, whether anything was ruled. This step
  is what makes it possible for a different AI (including the one that was working on this
  before you, and whichever one resumes after you) to pick the project back up accurately.
  Do not skip it or leave it for later.
- Do not silently correct or delete a wrong turn — record it. This project keeps a record
  of mistakes made along the way, not just the final clean state.
- Nothing here authorizes you to decide open governance/architecture questions on Viktor's
  behalf. docs/PHASE7_NEXT.md lists which open items are explicitly his to rule on ("Open —
  decisions") — treat those as off-limits for you to resolve, only to inform.
