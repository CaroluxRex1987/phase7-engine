## 1. Where the stated intent and the shipped code differ

**(1) "Macro … has no separate vote" / "Macro does not decide the CONSERVATIVE tier" — not delivered in full.** Work order G removed the macro *gate* from both CONSERVATIVE branches and removed `macro_bias` from `DecisionModel`. But `calculate_entry_quality` still applies `CONFLUENCE_BOOST_MULT` / `CONFLUENCE_PENALTY_MULT` (1.05 / 0.90) on `macro_bias`, and `entry_score >= AGGRESSIVE_ENTRY_SCORE_MIN (70)` is exactly what separates LONG/AGGRESSIVE from CONSERVATIVE. Concrete: base 66, trend ≥ 75, all three multipliers favourable → `66 × 1.05³ = 76.9` → **LONG**; the identical base with an opposing macro → `66 × 0.90 × 1.05² = 65.5` → **CONSERVATIVE LONG**. So macro still decides the tier across a band of entry scores. The requirement is satisfied as to the gate and not as to the boundary. (This is F4(3), restated as a plan-vs-execution gap: the ruling's wording is broader than what G shipped.)

**(2) "only a reversal pointing against the trade blocks it" — wrong signal named, and two blocker classes omitted.** `signal_blockers` takes `(direction, structure_regime, trend_exhaustion, momentum_divergence, divergence_direction)`. `reversal_direction` and `reversal_strength` — the fields literally named "reversal" — are not gate inputs at all; `tests/test_signal_confirms.py::test_the_signal_no_longer_takes_the_inputs_that_were_ruled_out` asserts `reversal_strength` was deliberately removed from the signature. The gate's direction-aware blocker is **momentum divergence**. And two of the three blocker classes are direction-blind: `structure_regime != "BULLISH TREND"` blocks a long (including **"NEUTRAL STRUCTURE"**, which therefore blocks both sides), and `trend_exhaustion` blocks regardless of direction. Work order F's own comment table says as much — "structure regime matches KEPT", "trend exhaustion KEPT", "momentum divergence BLOCKS ONLY WHEN IT POINTS AGAINST THE TRADE" — so the requirement bullet is a compression of that table that drops two rows. Practical effect: under a NEUTRAL structure regime no run can ever be confirmed, whatever the reversal state; and an opposing reversal built from HVN proximity alone (strength ≤ 20 before the 0.4 scale) blocks nothing, though its divergence/exhaustion components would. The requirement should say what the code does: three classes, one direction-aware.

**(3) Work order B item 3 — "a score nobody computed" — fixed for absent keys, not for the producers.** `_score_text` prints "not computed" only for non-finite input. But `models/entry_model.py`'s `default_response` still returns `"score": 0.0` with `"ema_pos_pts": 0` … `"struct_pts": 0`, and `indicators/trend_health.py`'s `default_response` returns `"trend_health": 0.0` — all finite, so the panel prints `ENTRY QUALITY : 0.00/100`, five `0.00/…` components and `TREND … (Score: 0.00/100)` where "not computed" is available and used for other fields. Note the asymmetry inside `default_response` itself: `distance_from_zone` was converted to NaN ("NaN is how this engine spells 'not located'") while `score` was left at 0.0 in the same dict. The commit message's own analysis stops at the router — "Latent: the router always sets the first three" — and never reaches the producer. Related: `signal_router._build_decision_object` still materialises `float(entry.get("score", 0.0))` and the five components at 0.0 defaults, so the panel's "absent fields print as 'n/a'" is unreachable from engine output. (This is my Part 4 observation, now with its provenance: the intent is real and the delivery is partial.)

**(4) Finding 4 — "the band is labelled for what it is" — the rename propagated the mislabel.** `entry_model` computes `distance_from_zone = (|close − zone_mid| / close) × 100` — distance from the band's **midpoint**. Commit `b0efe23` renamed the panel line "'away from zone' is 'away from the band'". The word "band" names the interval `[zone_lower, zone_upper]`, so the label is now further from the quantity than it was. This is F5; the finding stands and the commit message shows the gap between intent ("labelled for what it is") and delivery. The same rename left `entry_status` values ("ACTIVE ENTRY ZONE" etc.) and the data keys untouched, deliberately — fine, but the printed distance is the one line that got a new name and kept a wrong definition.

**(5) Finding 27 — "quotes the exchange's reply instead of discarding it" — the permanent record still discards it.** `_exchange_said` / `_http_error_body` do quote the reply, but only into the panel's error line. In `route_and_execute`, both the `_validate_engine_output` failure and the `if "error" in raw_output` path `return` **before** `decision_log.write`. So (a) the finding's title overstates delivery — the record has no copy of the exchange's words — and (b) more generally every failed run leaves no decision-log entry at all, so "why did the engine not act on date X" is unanswerable from the log months later. No rule is breached (a failed run is not an analysis and produces no major output), but it is a record-keeping gap my Parts 1–6 did not note. The commit message states the mechanism ("A failed fetch returns before the router writes the decision log"), so this is disclosed — the divergence is between the finding's title and what shipped.

**(6) Finding 26 — the exact-match lookup widened the silent-skip surface.** Commit `486f1a5` states it plainly: "an upper-case spelling the table does not list (e.g. '4H') is now unknown and skips the spacing and staleness checks, where before it was lower-cased and checked." So the fix for MEXC's "1M"/"60m" traded one silent loss of temporal checks for another: any unlisted spelling now disables spacing **and staleness** entirely. This refines F3 (below) rather than contradicting anything in Parts 1–6.

## 5. On the measure itself

I was invited to judge whether the deferred-then-measured order matters (Section 1). My view, with the interest stated: I have an interest in a pass, since "Compliant ratings count only from a run that passes", and the observations below all cut in my favour.

What makes the measure fair enough to run: the entries and their classifications were committed before the send; nothing was planted and the manifest integrity is preserved to the extent I can check it (file counts; the two counts I could verify by search); the "usable" filter excludes anything the first package reveals; and the project states its own caveat — three of the four change no trade — before asking for the score.

Three things a reader of the score should hold beside it:

1. **All four scored entries are named in the second message.** `1861208` states S1 ("the risk gate running before the weak-validation and lean checks"), `76c8cde` states S2 verbatim, `8b9ac1e` states S3, `7d0024e` states S4 ("The weak-validation WAIT decides nothing"). The "nothing in your package gives it away" test therefore passes only because the fixer's own narrative — which had already found and named all four — was reserved for Part 7. That is a legitimate design (it tests whether the code alone reveals what the narrative recorded), but it means the measure tests re-discovery of findings the fixer held, not discovery of anything unknown to the project.
2. **The threshold was set after a score existed.** Section 2 says so: the "two runs" rule was "decided after round 7's first run was scored". A threshold chosen after observing a result is weaker evidence than a pre-registered one, even though it changed no entry and no classification.
3. **The scorer is the fixer.** Claude chose the entries, wrote each "found means", and scores my text; the project owner checks. The definitions were locked before I wrote, which is the important safeguard, but selection and scoring are the party whose fixes I graded.

None of that makes the run invalid — my own count is 2/4 and I have said where — but a pass under this construction should be read as "the code still revealed two of four defects the fixer had already recorded", which is what it measures.
